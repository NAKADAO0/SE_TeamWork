# Lab2 六人分工与 Git 协作规范

第十二组 · 2026-11-15 · 对应《第十二组_Lab2设计文档_提交版.md》V1.1

本文以《第十二组_Lab2设计文档_提交版.md》及其生成的《第十二组_Lab2设计文档.pdf》为设计基准，展开第 9 章的六人分工、阶段交付与 Git 规则。成员 1–6 可直接替换为姓名。开发成员与平台内部 PM Agent、执行角色不同，不要求一人对应一个 Agent。仓库建立后落实以下协作约定；文档中的约定不代表分支保护或 CI 已经启用。

## 1. 分工原则

六人共同交付一条可运行主链：规格输入 → PM 分解 → 校验 → 编排 → 可视化与导出。先固定最小契约和 fixture，再并行实现。模块负责人负责该模块的代码、测试、接口说明与演示数据，集成人员不代替全组补测试。

P0 优先级高于 P1；只有主链、跨产品验证和异常场景通过后，才增加模拟执行或画布拖拽等功能。本文阶段表示依赖顺序，具体日期由课程截止时间倒排。

### 1.1 与设计文档对应的范围

- P0：规格输入与确认、真实 PM 调用、任务编辑、规则校验、确定性编排、图表联动、版本保存和 JSON/Markdown 导出。
- P1：主流程稳定后增加模拟执行、画布连线编辑和更多导入格式；模拟结果不作为案例产品已经开发成功的证据。
- 最终项目扩展：实际编码 Agent、代码沙箱、发布审批与完整质量治理。本轮不要求实现微信或内容社区产品本身。
- 通用性验收：聊天 MVP、内容社区 MVP 和未预置的第三类现场规格；真实调用留存人工质量检查记录，fixture 和回放明确标注模式。

本文增加的目录、命令和检查清单用于细化执行，不改变设计文档的功能优先级、负责人、验收编号和合并规则。设计调整时同步更新本文件，避免保留两套口径。

## 2. 六人职责与交付物

### 2.1 与设计文档第 9.1 节一致的分工

| 成员 | 主责 | 独立交付物 | 主要协作与复核 |
| --- | --- | --- | --- |

| 成员 3 | 共享契约与校验 | 数据模型、Schema、引用/覆盖/产物/DAG 规则及 fixture | 与 2、4 协调；4 复核规则 |

### 2.2 各模块的验收重点

| 成员 | 细化要求 |
| --- | --- |
| 成员 1 | 任务表、详情与问题定位可用；确认版只读，编辑创建新草稿；图列表共享同一 plan_ref |
| 成员 2 | 同一 PM 处理三类规格；非法输出最多一次修订；关键缺口转澄清；实时、离线和回放模式不混淆 |
| 成员 3 | 错误能定位字段与条目；环返回真实闭合路径；输入引用、类型、需求实现/验证覆盖符合契约 |
| 成员 4 | 固定任务、模板和配置产生相同编排；优先级和 ID 排序稳定；资源批次合法，阻塞有解释 |
| 成员 5 | expected_revision 冲突返回 409；作业绑定输入快照；新修订重新校验编排；确认与导出固定版本 |
| 成员 6 | 节点、列表、详情和导出一致；覆盖 V01–V14；组织实际验收记录，不将未执行场景标为通过 |

成员 5 的后端工作量较集中：成员 2 自行实现 PM 适配与作业执行函数，成员 3/4 自行实现可被路由调用的领域服务；成员 5 统一接线和持久化。成员 6 只组织端到端验收，各模块负责人修复本人问题。

P1 分工：成员 4 负责模拟调度状态，成员 5 负责运行记录/API，成员 6 负责运行图与演示；成员 1 可补画布编辑，成员 2/3 优先提升生成质量和模板校验。不能为了让每人都写一个 Agent 而增加无必要角色。

## 3. 共享边界与交接方式

| 协作双方 | 先固定的交接件 | 约束 |
| --- | --- | --- |
| 1 ↔ 5 | OpenAPI、请求示例、作业状态、修订冲突错误 | 前端只调用服务端；不直接访问 SQLite |
| 2 ↔ 3 | PM 输入输出 JSON、错误反馈、澄清状态 | 模型返回值先校验，禁止各自定义另一种任务结构 |
| 3 ↔ 4 | 校验报告、固定 TaskPlan、执行计划 Schema | 编排不重复实现另一套校验规则；先通过正式校验器 |
| 4 ↔ 6 | nodes、edges、topological_levels、batches、bindings | 图只渲染领域结果，坐标不影响调度 |
| 2/3/4 ↔ 5 | 服务函数签名、事务归属、错误模型 | 领域服务返回数据；持久化由统一 repository 层处理 |
| 1 ↔ 6 | 导航、样式、共享状态、节点选择事件 | 共用 API client 和当前 plan revision，不复制任务业务状态 |

共享契约由成员 3 主责，数据库迁移与 API 总装由成员 5 主责，编排规则由成员 4 主责，前端公共组件由成员 1/6 协同维护。主责表示协调与审查责任，不禁止其他人修改。

变更公共字段前，在 Issue 中说明字段变化、原因、兼容影响、受影响模块及迁移办法；先更新契约和 fixture，再改提供方与消费者。成员 3 和受影响负责人至少各一人确认后合并。不能在私有分支上单方面改变状态名、边方向或版本语义。

## 5. 开发阶段与验收门槛

下表与设计文档第 9.2 节采用相同的阶段名称、联合工作和放行标准。

| 阶段 | 联合工作 | 放行标准 |
| --- | --- | --- |
| S0 契约与示例 | 固定规格、任务、编排、错误与 API 样例 | 各模块可用同一份 fixture 独立开发 |
| S1 最小主链 | 串联输入、PM、校验、编排、图与导出 | 至少一个完整规格在服务端跑通 |
| S2 规则与编辑 | 补覆盖、产物引用、容量、修订和编辑场景 | 正常与异常输入均可定位和处理 |
| S3 跨产品联调 | 执行 V01–V14，检查实时规划和现场输入 | 留存实际结果、缺陷与修复记录 |
| S4 交付冻结 | 修复阻断、检查新环境启动、演练与归档 | 稳定标签、使用说明和验收材料齐全 |

阶段执行安排：S0 由成员 3 组织契约，成员 2/4 提供规划与编排样例，成员 5 固定 API，成员 1/6 确认界面数据；S1 各人串联本人模块；S2 各人补测试、错误处理和编辑规则；S3 由成员 6 组织端到端、成员 2 主导三类规格，其他成员验证本人边界；S4 全员修复阻断并补齐交付材料。验收编号统一引用设计文档第 8.3 节 V01–V14，不另建一套场景编号。

尽量在总可用工期前 30% 内完成 S1，为联调留下空间。每天同步三项：已合并成果、阻塞事项、下一交接件；不把“正在写”当作完成。阻塞优先用 Issue 记录具体输入、预期、实际和日志。

## 6. Git 分支策略

### 6.1 使用轻量主干开发

推荐 **main + 短期功能分支 + Pull Request**。六人课程项目不额外维护长期 develop 分支，减少同步与合并成本。main 始终保持可启动、基础检查通过；演示版本使用带说明的 tag。

| 分支 | 命名示例 | 规则 |
| --- | --- | --- |
| main | main | 受保护，通过 PR 合并，不直接推送 |
| feat | feat/12-pm-plan | 一个独立可验收功能，尽量 1–2 个开发日内合并 |
| fix | fix/27-cycle-path | 一个缺陷及相关修复 |
| docs | docs/31-lab2-design | 设计、说明或示例材料 |
| chore | chore/18-ci-checks | 工具配置或独立测试完善；test 保留为提交类型 |

数字为实际 Issue 编号，示例数字不表示已有 Issue。不建立“成员1分支”之类长期个人分支；大功能拆为兼容小 PR，用 Draft PR 提前暴露接口变更。

### 6.2 常规操作示例

以下命令在团队建立 Git 远程仓库后使用；当前仅文档目录无需为了本次修订自动初始化或推送。

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/12-pm-plan

# 完成一段可检查修改，并运行与本模块有关的检查
git status --short
git add backend/app/planner backend/tests/planner
git diff --cached
git commit -m "feat(planner): generate task plans from design specs"
git push -u origin feat/12-pm-plan
```

暂存实际修改的文件，提交前检查 diff；不要因使用 git add . 把数据库、密钥或调试产物一起提交。示例路径在项目实现相应模块后才适用。

### 6.3 分支同步与冲突

个人独占分支允许 rebase 到最新 main；共享分支使用 merge，避免改写别人历史。功能分支尚未推送时可自由整理本人的提交。需要重写已推送个人分支时先确认无人基于它开发，只使用 --force-with-lease，禁止对 main 或共享分支强推。

```powershell
git fetch origin
git rebase origin/main
# 出现冲突后先理解两侧意图，修改文件，再暂存明确的冲突文件
git add path/to/resolved-file
git rebase --continue
# 放弃本次 rebase 可用 git rebase --abort
```

共享分支需要同步时改用 git merge origin/main。冲突解决后重新运行受影响检查；公共契约、状态转换与迁移文件的冲突必须找相关负责人共同确认，不能机械选择全部 ours/theirs。保留他人未提交修改，不用 reset --hard 或清理命令掩盖冲突。

## 7. Commit、PR 与评审规范

### 7.1 Commit 规范

格式：type(scope): 简明说明。说明可中文或英文，同一项目尽量一致；一个提交表达一个完整意图。

| type | 使用场景 | 示例 |
| --- | --- | --- |
| feat | 新功能 | feat(orchestrator): add role capacity scheduling |
| fix | 缺陷修复 | fix(validation): report an actual dependency cycle |
| docs | 文档 | docs(lab2): define prototype acceptance scenarios |
| test | 测试 | test(api): reject stale plan revisions |
| refactor | 不改外部行为的结构调整 | refactor(storage): extract plan repository |
| chore | 依赖、工具或构建配置 | chore(ci): run backend and frontend checks |

不要使用“update”“改好了”“最终版”等无法说明内容的消息。公开契约不兼容时使用 feat(contracts)!: ...，在 PR 说明迁移与兼容影响；不能只改版本号不解释。

### 7.2 Pull Request 模板

```text
标题：feat(orchestrator): generate deterministic execution batches

关联 Issue：Closes #实际编号
问题与结果：哪个输入触发什么问题，修改后怎样表现。
主要改动：本 PR 的关键行为与涉及模块。
契约影响：新增/修改字段、兼容性、迁移和受影响调用方。
验证：实际执行的命令、结果；交互变化附截图或短录屏。
演示步骤：使用哪个公开 fixture，怎样观察结果。
限制：仍存在的问题、P1 及最终项目扩展项、真实模型/离线模式说明。
```

PR 尽量一次只解决一个问题，排除生成文件后约 300 行以内作为参考；超过时拆分或说明原因，不以行数阻止合理变更。禁止把不相关重构、格式化全仓与功能混在一起。

### 7.3 合并条件

1. 相关检查通过，PR 可复现，阻断评审意见已处理。
2. 至少一名非作者批准；公共契约、数据库迁移、编排状态规则需主责或其指定替补评审。
3. 跨模块 PR 由受影响调用方确认接口兼容；作者不得自批自合并。
4. 更新了相关契约、fixture、说明或迁移；真实调用证据已脱敏。
5. 与 main 同步且无冲突，使用 squash merge，合并后删除短期分支。

有权限且非作者的评审人可执行合并，不必全部等待组长。若使用 GitHub/GitLab，按平台能力配置 main 保护、必需检查和评审规则；这些设置需要仓库管理权限，写入本规范不代表已经生效。

## 8. CI、文件与配置规范

### 8.1 最小检查矩阵

| 修改范围 | 必须检查 | 负责人 |
| --- | --- | --- |
| 后端领域/API | 格式与静态检查、相关 pytest、契约兼容检查 | PR 作者；成员 5 维护后端统一命令 |
| 前端 | 类型检查、构建、相关组件测试 | PR 作者；成员 1/6 维护命令 |
| 契约/模板 | Schema/模型导出一致、全部共享 fixture、编排回归 | 成员 3 协调 |
| 跨模块主链 | 固定规格 → 使用 fixture 响应完成 PM 生成步骤 → 校验 → 编排 → 图/导出一致 | 成员 6 维护，作者修复 |
| 文档/案例 | 链接、JSON 示例、命令及演示材料人工检查 | 文档作者与评审人 |

CI 不调用收费真实模型，也不依赖个人密钥；实时模型质量单独做人工验证并保存记录。初始化项目时统一检查入口与依赖锁文件，不要求为纯文档小改动运行无关完整模型测试。

## 9. 版本发布与演示故障处理

建议标签按里程碑使用 v0.1.0（最小闭环）、v0.2.0（跨产品验证）、v1.0.0-lab2（课堂交付）。标签必须指向通过检查的 main 提交，带发布说明；已供他人使用的标签不重写。

演示前从全新目录按 README 安装并启动，确认环境变量、端口、示例数据、真实模型和离线回放标签。发布包附实际测试结果与已知限制；未做的测试注明未做。

main 出现回归时，先停止继续合入相关功能，创建修复 PR；紧急恢复可使用 git revert 撤销问题合并提交，通过正常评审与检查后合并。不要对共享主干使用 reset + 强推。演示前预留修复窗口，避免临上课合入无关功能。

## 10. 每个任务的完成定义

任务关闭必须同时具备：可运行交付物、适用检查的实际通过结果、接口/文档/fixture 同步、非作者评审、已合并且主链仍可用。UI 变化有截图或录屏；模型相关变化注明生成模式与质量检查；契约变化有调用方验证。

最终交付由六人共同完成：成员 1 讲输入与编辑，成员 2 讲 PM 分解，成员 3 讲规格与校验，成员 4 讲编排，成员 5 讲服务与版本，成员 6 串联可视化、验证和演示。若课堂时间短，由一人主讲，其余成员负责各模块答辩。
