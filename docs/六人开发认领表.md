# Lab2 六人开发认领表

从 feat/lab2-demo 开工。每位成员负责一项可演示的成果，并在自己的 PR 中附上验收输入和实际结果。

| 成员 | 你的第一件事 | 你负责交付什么 | 谁来接、怎么验 |
| --- | --- | --- | --- |
| 1 · 需求与编辑 | 打开 workspace.html 和 demo/app.js，用自定义产品走一遍输入流程 | 能确认规格、查看生成状态、修改任务并保存的工作台 | 交给 6 联调。修改任务验收条件后保存，图谱详情显示新条件，旧修订仍可查询 |
| 2 · PM 生成 | 从 demo/planner.js 的输入输出出发，用 3 的任务格式接一次真实模型调用 | 服务端 PM 生成函数，返回任务草稿或澄清问题，并保留生成模式 | 交给 5 调用、3 校验。输入现场新产品时生成对应任务，模型故障时显示实际错误 |
| 3 · 数据契约与校验 | 选 examples/chat.json 中一项需求，给出从规格到任务再到计划的完整 JSON 样例，另附一个带环样例 | 共享字段定义、合法样例和校验函数，约定任务 ID、依赖方向及错误字段路径 | 样例交全组，校验函数交 5。删除验证任务能定位缺口，引入环能指出闭合路径 |
| 4 · 编排算法 | 打开 demo/compiler.js，固定同一组任务，分别尝试一个和两个 QA 槽位 | 消费已校验任务的编排函数，输出拓扑层、执行批次、角色绑定和等待原因 | 交给 5 接 API、6 画图。调整容量后，每批人数符合限制，业务依赖边保持一致 |
| 5 · 后端与版本 | 和 3 对齐请求、响应及一份错误样例，先让工作台通过 API 读取固定计划 | 串联 PM、校验、编排的 API，以及 SQLite 保存、修订查询和导出 | 交给 1 和 6。保存后重新打开能读回同一修订，旧修订写入返回 409，导出与查询一致 |
| 6 · 图谱与集成 | 打开 graph.html 和 demo/graph.js，用 3、4 的样例渲染一个批次并选中任务 | 能读取指定计划修订的 DAG、节点详情，以及端到端演示与验收记录 | 和 1 核对图表联动，和 4 核对边方向。图、列表、导出的任务 ID 和依赖一致，按 V01–V14 记录实际结果 |

## 第一次联调怎么做

1. **先统一一个例子。** 3 发出合法与错误样例，5 发出对应 API 样例。1、2、4、6 各自确认能取到自己需要的字段。
2. **六人同时做各自那一行。** 1 和 6 先用固定数据做界面，2 调真实模型，3 和 4 分别实现校验与编排，5 用样例打通保存、查询和导出。
3. **按依赖接入。** 5 先接 3、4，再将固定任务替换为 2 的真实输出。1 从工作台提交自定义规格，6 打开这次生成的修订并与导出核对。
4. **交给全组验收。** 6 组织跨产品联调，各人修复本人模块的问题。S0–S4 阶段、V01–V14 验收口径和 Git 合并要求见[协作规范](六人分工与Git协作规范.md)。

## 出现问题找谁

模型漏拆一项需求找 2，校验器未报告该缺口找 3。批次超容量找 4，批次正确但图上连线错误找 6。保存了错误修订找 5，表单提交了错误字段找 1。跨模块问题在同一 Issue 附上规格、计划修订、预期和实际结果，由接口两端共同复现。
