# 契约与校验规范

> 成员 3（数据契约与校验）交付说明 · schema_version `1.0`
>
> 适用范围：设计规格（DesignSpec）、工作流模板（WorkflowTemplate）、任务计划（TaskPlan）、执行计划（ExecutionPlan）与校验报告（ValidationReport）。后端、前端与测试共用本规范，**不要手改 Schema 文件**，以模型导出结果为准。

## 1. 单一来源与交付物

| 交付物 | 位置 | 说明 |
| --- | --- | --- |
| 数据模型（单一来源） | `backend/app/contracts/models.py` | dataclass + 字段元数据；字段顺序即文档顺序 |
| JSON Schema（导出） | `backend/app/contracts/schema/*.schema.json` | 由模型导出，勿手改；`export_schema --check` 校验一致 |
| Schema 导出/检查工具 | `backend/app/contracts/schema.py`、`export_schema.py` | `model_schema` / `contract_schemas` / `write_schemas` / `check_schemas` |
| 旧案例迁移 | `backend/app/contracts/normalize.py` | 旧 `examples/*.json` → 契约草稿 + 缺口报告 |
| 校验器 | `backend/app/validation/validator.py` | 规格/任务计划/执行计划三个入口 |
| 错误码表 | `backend/app/validation/codes.py` | 与本文第 8 节同步维护 |
| 结构检查 | `backend/app/validation/structure.py` | 用导出的 Schema 遍历输入，产出带字段路径的问题对象 |
| 共享样例 | `examples/contracts/`、`templates/default-workflow.json` | 合法样例、执行计划、错误样例与预期报告 |
| fixture 生成 | `backend/tools/build_fixtures.py` | `--write` 生成派生文件，`--check` 检查是否最新 |

同一份 Schema 同时驱动：结构校验（`structure.check_structure`）、外部工具/OpenAPI 导出、fixture 结构测试。因此模型、Schema、校验三者的差异只有一处来源。

## 2. 统一引用、版本与摘要

设计文档 §3.2 规定的统一对象在这里落为引用字段：

| 对象 | 身份 | 引用字段 |
| --- | --- | --- |
| DesignSpec | `spec_id` + `version` | `spec_ref: {spec_id, version}` |
| WorkflowTemplate | `template_id` + `version` | `template_ref: {template_id, version}` |
| TaskPlan | `plan_id` + `revision` | `plan_ref: {plan_id, revision}` |
| ExecutionPlan | `execution_plan_id` | `plan_ref`、`validation_ref` |

- `schema_version` 独立于业务版本，表示**格式版本**，当前固定 `"1.0"`；格式不兼容变更才升级。
- 修订号从 1 递增。PUT/确认请求必须带 `expected_revision`（或 `expected_version`），不匹配返回 `409`，见 `REVISION_MISMATCH`。
- 引用的规格/模板版本必须与当前版本一致（`REF_VERSION_MISMATCH`）；旧版本报告在被引用后不得复用（执行计划校验 `EXEC_VALIDATION_REF_MISMATCH`）。
- **内容摘要**：对对象做规范化 JSON（键排序、紧凑分隔符、UTF-8 原文、数组保持契约顺序）后取 SHA-256 小写十六进制，64 位。函数：`backend.app.contracts.content_digest(value)`。
  - 执行计划保存 `spec_digest`、`template_digest`、`config_digest`（对 TaskPlan 内的 `config` 计算）。
  - 校验报告保存 `content_digest`（被校验对象的摘要），执行计划用 `validation_ref.report_digest` 引用报告的摘要。
  - 任一侧内容变化即摘要变化，用于 V14“固定修订导出可核对”。

## 3. JSON 编码约定

- 文件统一 UTF-8、LF；示例 fixture 键排序输出（`build_fixtures.py` 统一生成）。
- 可选字段**缺省**表示不存在，不要写 `null`（结构校验会报 `FIELD_TYPE`）。`to_jsonable` 已自动省略 `None`。
- 整数字段（`priority`、`version`、`revision`、`max_concurrency`、`role_capacity` 值、`estimated_effort.value`）不接受浮点/字符串。
- 所有 `id` 字段符合 `^[A-Za-z][A-Za-z0-9_-]*$`，建议大写前缀：`R*` 需求、`M-*` 模块、`I-*`/`P-*` 设计条目、`C-*` 约束、`*` 任务、`O-*` 产物、`PLAN-*`/`SPEC-*`/`TPL-*`/`EXEC-*`。

## 4. 对象字段契约

### 4.1 DesignSpec（设计规格）

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `schema_version` | string，必填 | 格式版本 |
| `spec_id` | ID，必填 | 规格标识 |
| `version` | int ≥1，必填 | 规格版本 |
| `product` | string，必填 | 产品/案例名称 |
| `scope` | object，必填 | 产品范围：`goal`（目标）、`included`（首期功能，至少 1 条）、`excluded`（明确排除项，可为空） |
| `requirements` | array ≥1 | 需求条目：`{id, goal, acceptance}`，`id` 在规格内唯一 |
| `modules` | array ≥1 | 模块职责：`{id, responsibility, requirement_ids[]}`；`requirement_ids` 引用真实需求 |
| `design_items` | array ≥1 | 设计内容：`{id, kind, description, requirement_ids[]}`；`kind` 建议 `page/interface/entity/rule/other`（当前为自由字符串） |
| `constraints` | array ≥1 | 约束：`{id, category, detail, status}`；`status ∈ specified / not_applicable / unspecified`，未指定用 `unspecified` 显式记录 |

校验要点：各列表 ID 唯一；模块/设计条目引用的需求必须存在；需求应被至少一个模块或设计条目映射（`SPEC_REQUIREMENT_UNMAPPED` 警告）；`unspecified` 约束产生警告（`SPEC_CONSTRAINT_UNSPECIFIED`）。

### 4.2 WorkflowTemplate 与 RunConfig（工作流模板与运行配置）

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `template_id` / `version` | ID / int ≥1 | 模板身份 |
| `name` / `description` | string | 模板名称与说明 |
| `stages` | array ≥1 | 允许的阶段，如 `implement/verify/integrate` |
| `allowed_roles` | array ≥1 | 允许角色，如 `backend/frontend/qa` |
| `require_verification` | bool | 是否要求每条需求都有验证任务（false 时缺验证降为警告） |
| `config.max_concurrency` | int ≥1 | 全局并发上限 |
| `config.role_capacity` | object，值 int ≥1 | 各角色容量；使用的角色必须有容量 |
| `config.ordering` | array ≥1，元素 ∈ `priority`/`task_id` | 稳定排序键；缺少 `task_id` 时警告（V07 确定性） |

### 4.3 TaskPlan 与 Task（任务计划与任务卡）

TaskPlan 字段：`schema_version, plan_id, revision, spec_ref, template_ref, config, generation_mode, tasks[], assumptions[], clarifications[]`。
`generation_mode ∈ live_llm / offline_rule / fixture_replay / curated_example`：前端与导出必须明示实际模式（V13）；`curated_example` 表示预编排案例，`fixture_replay` 专指回放已保存的生成响应。

Task 字段与规则：

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | ID，计划内唯一 | 任务 ID 由规划器/人工确定，编排阶段**不得重造** |
| `title` / `description` | string | 任务卡标题与描述 |
| `requirement_ids` | array ≥1 | 需求来源；多需求来源（如旧案例 `"R1、R2"`）规范化为数组 |
| `module_ids` / `design_refs` | array | 引用规格中的模块/设计条目；非 `support` 任务为空时告警（`TASK_DESIGN_REF_EMPTY`） |
| `kind` | enum | `implementation / verification / integration / support` |
| `stage` | string | 必须在模板 `stages` 中 |
| `role` | string | 必须在模板 `allowed_roles` 中 |
| `inputs` | array | 输入声明，见 §5 |
| `outputs` | array ≥1 | 产物声明：`{id, type, description}`，`id` 在同一计划内唯一 |
| `acceptance` | array ≥1 | 可检查的验收标准 |
| `depends_on` | array | 前置任务：`{task_id, reason}`；**边从前置指向当前任务** |
| `priority` | int ≥0 | 越小越优先；排序键之一 |
| `estimated_effort` | object | `{value(≥1 正整数), unit, basis}` |

### 4.4 ExecutionPlan（执行计划）

字段：`schema_version, execution_plan_id, plan_ref, spec_digest, template_digest, config_digest, nodes[], edges[], topological_levels[], batches[], bindings[], validation_ref`。

- `nodes`：每个任务恰一次，`{task_id, role, stage, priority}` 必须与任务卡一致。
- `edges`：`{from_task, to_task}`，方向为**前置 → 当前**；必须与 `depends_on` 去重后的边集完全一致。
- `topological_levels`：`[["C1"], ["C2","C3"], ...]`，每条边的前置必须位于更早的层。
- `batches`：每批任务集合，大小不超过 `max_concurrency`，同角色数量不超过 `role_capacity`，且前置任务必须在更早批次。
- `bindings`：每个任务恰一次槽位分配，`{task_id, global_slot, role_slot}`；`global_slot ∈ [1, max_concurrency]`，`role_slot ∈ [1, role_capacity[role]]`；同一批内槽位不得冲突。
- `validation_ref`：`{plan_id, revision, report_digest}`，指向该修订的校验报告；报告被阻断或摘要不符时执行计划作废。
- 执行计划只承载领域结果，供列表、图与导出复用（V11）；任务/边不在此层增删。

### 4.5 ValidationReport（校验报告）

| 字段 | 说明 |
| --- | --- |
| `schema_version` | 格式版本 |
| `target` | `{kind: design_spec/task_plan/execution_plan, spec_id?, version?, plan_id?, revision?, execution_plan_id?}` |
| `content_digest` | 被校验对象的规范化摘要 |
| `blocked` | 是否存在 error（error 阻止编排/确认） |
| `summary` | `{errors, warnings}` |
| `issues` | 统一问题对象数组，见下 |
| `coverage` | 仅任务计划报告携带：逐需求实现/验证任务与覆盖率 |

统一问题对象：`code`（大写下划线，见第 8 节）、`severity`（`error` / `warning`）、`object_id`（出问题的对象 ID，如任务/需求/计划）、`field_path`（JSON 路径）、`message`（中文可读说明）、`related_ids`（相关对象）、`suggested_action`（修复建议）。

## 5. ID 约定、产物与依赖方向

- **任务 ID**：由任务规划产出并固定，后续编辑保留原 ID；编排、校验、图、导出均以任务 ID 关联（V11）。
- **依赖方向**：`depends_on` 中 `{task_id: "C1"}` 表示**当前任务依赖 C1**；归一化为边时记录为 `from_task: C1, to_task: 当前任务`。
- **产物引用**：每个输出在计划内唯一（`O-*`）。输入声明：
  - `{source: "design", ref: "<规格中的设计条目 ID>", type: "design_contract"}`；
  - `{source: "task_output", ref: "<生产任务 ID>/<产物 ID>", type: "<产物类型>"}`。
- **直接依赖规则（P0）**：直接消费某任务产物时，必须在 `depends_on` 中声明该生产任务的直接依赖（`ARTIFACT_PRODUCER_DEPENDENCY_MISSING`）。不通过其他任务传递代替。
- 设计输入的类型必须是 `design_contract`；任务产物输入的类型必须与生产任务声明的产物类型一致（`ARTIFACT_TYPE_MISMATCH`）。
- 不允许自引用（`ARTIFACT_SELF_REFERENCE`）、引用不存在的生产任务/产物（`ARTIFACT_PRODUCER_UNKNOWN` / `ARTIFACT_OUTPUT_UNKNOWN`）、格式错误的 `ref`（`ARTIFACT_INPUT_REF_INVALID`）。

## 6. 校验接口

```python
from backend.app.validation import (
    validate_design_spec,      # (spec, *, expected_version=None) -> ValidationReport
    validate_task_plan,        # (plan, *, spec, template=None, expected_revision=None) -> ValidationReport
    validate_execution_plan,   # (execution_plan, *, task_plan, validation_report=None, spec=None, template=None) -> ValidationReport
)
```

- 入参可以是 JSON 字典，也可以是通过 `from_dict` 构造的 dataclass；报告返回 `ValidationReport`，用 `to_jsonable(report)` 得到可直接 `json.dumps` 的字典（也是落库/接口格式）。
- 校验顺序：**结构（Schema）→ 语义**。结构错误不会阻断后续可执行的语义检查（例如缺字段时仍会检查其余检查面），但报告 `blocked=true`。
- 严重级别默认 `error`；仅以下为 `warning`：`SPEC_CONSTRAINT_UNSPECIFIED`、`SPEC_REQUIREMENT_UNMAPPED`、`TASK_DESIGN_REF_EMPTY`、`CONFIG_ORDERING_NONDETERMINISTIC`、`require_verification=false` 时的缺验证任务。
- HTTP 语义映射（供成员 5 API 使用）：请求结构非法 `400`；对象不存在 `404`；版本/修订冲突 `409`（`REVISION_MISMATCH`、`EXEC_PLAN_REF_MISMATCH`、`EXEC_VALIDATION_STALE` 等）；校验存在 error、阻止确认 `422`；作业/依赖服务不可用 `503`。

一次典型调用：

```python
import json
from backend.app.validation import validate_task_plan

spec = json.load(open("examples/contracts/chat/design-spec.json", encoding="utf-8"))
plan = json.load(open("examples/contracts/chat/task-plan.json", encoding="utf-8"))
template = json.load(open("templates/default-workflow.json", encoding="utf-8"))
report = validate_task_plan(plan, spec=spec, template=template)
assert report.blocked is False and report.summary.errors == 0
```

## 7. 字段路径约定

`field_path` 是相对于被校验文档的路径，数组用 `[下标]`：

| 示例 | 含义 |
| --- | --- |
| `tasks[0].title` | 第 1 个任务的 title |
| `tasks[5].inputs[1].ref` | 第 6 个任务第 2 个输入引用 |
| `tasks[1].depends_on[0].task_id` | 第 2 个任务第 1 条前置任务 |
| `config.role_capacity.qa` | qa 角色容量 |
| `spec.requirements[1]` | **被引用规格**中第 2 条需求（覆盖检查使用 `spec.` 前缀指向规格文档） |
| `edges[0]`、`batches[1]`、`topological_levels[2]` | 执行计划结构位置 |
| `$` | 文档根 |

问题对象的 `object_id` 与 `field_path` 配合定位：例如 `COVERAGE_VERIFICATION_MISSING` 的 `object_id=R2`、`field_path=spec.requirements[1]`、`related_ids=[C4, C5]` 表示“R2 缺少验证任务，相关的是 C4/C5”。

## 8. 错误码表

### 8.1 数据结构（Schema 驱动）

| code | 触发条件 | 典型 field_path |
| --- | --- | --- |
| `FIELD_REQUIRED` | 缺少必填字段 | `tasks[0].title` |
| `FIELD_TYPE` | 类型不符（含 `null`） | `tasks[0].priority` |
| `FIELD_UNKNOWN` | 出现契约外字段 | `tasks[0].unexpected` |
| `FIELD_EMPTY` | 必填字符串/数组/对象为空 | `tasks[0].acceptance`、`modules` |
| `FIELD_PATTERN` | 不符合模式（如 ID 规则、摘要 64 位十六进制） | `spec_id` |
| `FIELD_RANGE` | 数值越界 | `config.max_concurrency` |
| `FIELD_CHOICE` | 枚举值非法 | `tasks[0].kind` |

### 8.2 规格完整性与引用

| code | 触发条件 | 典型 field_path | 级别 |
| --- | --- | --- | --- |
| `SPEC_REQUIREMENT_ID_DUPLICATE` | 需求 ID 重复 | `requirements[i].id` | error |
| `SPEC_MODULE_ID_DUPLICATE` | 模块 ID 重复 | `modules[i].id` | error |
| `SPEC_DESIGN_ITEM_ID_DUPLICATE` | 设计条目 ID 重复 | `design_items[i].id` | error |
| `SPEC_CONSTRAINT_ID_DUPLICATE` | 约束 ID 重复 | `constraints[i].id` | error |
| `SPEC_MODULE_REQUIREMENT_UNKNOWN` | 模块引用不存在的需求 | `modules[i].requirement_ids[j]` | error |
| `SPEC_DESIGN_ITEM_REQUIREMENT_UNKNOWN` | 设计条目引用不存在的需求 | `design_items[i].requirement_ids[j]` | error |
| `SPEC_REQUIREMENT_UNMAPPED` | 需求未被任何模块/设计条目映射 | `requirements[i]` | warning |
| `SPEC_CONSTRAINT_UNSPECIFIED` | 约束标记为 unspecified | `constraints[i].status` | warning |
| `REF_SPEC_UNKNOWN` | `spec_ref.spec_id` 与传入规格不符 | `spec_ref.spec_id` | error |
| `REF_TEMPLATE_UNKNOWN` | `template_ref.template_id` 与传入模板不符 | `template_ref.template_id` | error |
| `REF_VERSION_MISMATCH` | 引用的规格/模板版本不是当前版本 | `spec_ref.version` | error |
| `REF_REQUIREMENT_UNKNOWN` | 任务引用不存在的需求 | `tasks[i].requirement_ids[j]` | error |
| `REF_MODULE_UNKNOWN` | 任务引用不存在的模块 | `tasks[i].module_ids[j]` | error |
| `REF_DESIGN_UNKNOWN` | 任务引用不存在的设计条目 | `tasks[i].design_refs[j]` | error |

### 8.3 任务、覆盖与产物

| code | 触发条件 | 典型 field_path | 级别 |
| --- | --- | --- | --- |
| `TASK_ID_DUPLICATE` | 任务 ID 重复 | `tasks[i].id` | error |
| `TASK_ROLE_NOT_ALLOWED` | 角色不在模板 `allowed_roles` | `tasks[i].role` | error |
| `TASK_STAGE_NOT_IN_TEMPLATE` | 阶段不在模板 `stages` | `tasks[i].stage` | error |
| `TASK_DESIGN_REF_EMPTY` | 非 support 任务无设计条目引用 | `tasks[i].design_refs` | warning |
| `COVERAGE_IMPLEMENTATION_MISSING` | 需求没有实现任务 | `spec.requirements[i]` | error |
| `COVERAGE_VERIFICATION_MISSING` | 需求没有验证任务 | `spec.requirements[i]` | error（`require_verification=false` 时 warning） |
| `OUTPUT_ID_DUPLICATE` | 产物 ID 在计划内重复 | `tasks[i].outputs[j].id` | error |
| `ARTIFACT_INPUT_REF_INVALID` | `task_output` 的 ref 不是 `<任务>/<产物>` | `tasks[i].inputs[j].ref` | error |
| `ARTIFACT_PRODUCER_UNKNOWN` | 生产任务不存在 | `tasks[i].inputs[j].ref` | error |
| `ARTIFACT_OUTPUT_UNKNOWN` | 生产任务未声明该产物 | `tasks[i].inputs[j].ref` | error |
| `ARTIFACT_TYPE_MISMATCH` | 输入类型与产物类型/设计输入类型不符 | `tasks[i].inputs[j].type` | error |
| `ARTIFACT_DESIGN_REF_UNKNOWN` | 设计输入引用不存在的设计条目 | `tasks[i].inputs[j].ref` | error |
| `ARTIFACT_PRODUCER_DEPENDENCY_MISSING` | 消费产物但未直接依赖生产任务 | `tasks[i].depends_on` | error |
| `ARTIFACT_SELF_REFERENCE` | 输入引用自身产物 | `tasks[i].inputs[j].ref` | error |

### 8.4 依赖图

| code | 触发条件 | 典型 field_path |
| --- | --- | --- |
| `DEPENDENCY_UNKNOWN` | 前置任务不存在 | `tasks[i].depends_on[j].task_id` |
| `DEPENDENCY_SELF` | 任务依赖自身 | `tasks[i].depends_on[j].task_id` |
| `DEPENDENCY_DUPLICATE` | 同一前置任务重复声明 | `tasks[i].depends_on[j].task_id` |
| `DEPENDENCY_CYCLE` | 存在依赖环；`related_ids` 为真实闭合路径（首尾相同），message 含 `A → B → A` | 回边对应的 `depends_on[j].task_id` |

> 环的处理：校验器只报告，不自动删边；下游任务称为“受环影响”。修复由用户决定，删除或重排依赖后重新校验（V05）。

### 8.5 配置与修订

| code | 触发条件 | 典型 field_path | 级别 |
| --- | --- | --- | --- |
| `CONFIG_ROLE_UNKNOWN` | `role_capacity` 含模板未允许角色 | `config.role_capacity.<role>` | error |
| `CONFIG_ROLE_CAPACITY_MISSING` | 任务使用角色但没有容量配置 | `config.role_capacity` | error |
| `CONFIG_ORDERING_NONDETERMINISTIC` | `ordering` 缺少 `task_id`（V07 稳定性） | `config.ordering` | warning |
| `REVISION_MISMATCH` | `expected_revision`/`expected_version` 与当前不符（HTTP 409） | `revision` / `version` | error |

### 8.6 执行计划

| code | 触发条件 |
| --- | --- |
| `EXEC_PLAN_REF_MISMATCH` | `plan_ref` 与传入任务计划的 plan_id/revision 不一致 |

## 11. 旧案例迁移（`backend/app/contracts/normalize.py`）

旧 `examples/chat.json`、`examples/chat-plan.json` 等保持原样；迁移函数只读旧文件，输出契约草稿 + **缺口报告**：

```python
from backend.app.contracts import normalize_legacy_examples

spec_result, plan_result = normalize_legacy_examples(
    legacy_spec, legacy_plan, spec_id="SPEC-CHAT-LEGACY", plan_id="PLAN-CHAT-LEGACY"
)
spec_result.document   # 符合契约结构的草稿（模块/设计条目为空，待补全）
spec_result.gaps       # [MigrationGap(code, object_id, field_path, message, ...)]
```

- `source: "R1、R2"` → `requirement_ids: ["R1","R2"]`；`depends_on` 字符串 → `{task_id, reason}` 对象。
- 类型推断：`qa` 且标题含“联调/验收/端到端”→ `integration`；`qa`/含“验证”→ `verification`；其余 → `implementation`。
- 按需求补充 `module_ids/design_refs/inputs/outputs/priority/estimated_effort` 占位并记录缺口。

缺口码：`LEGACY_SCOPE_INFERRED`、`LEGACY_MODULES_MISSING`、`LEGACY_DESIGN_ITEMS_MISSING`、`LEGACY_CONSTRAINTS_MISSING`、`LEGACY_SOURCE_MISSING`、`LEGACY_KIND_INFERRED`、`LEGACY_ROLE_MAPPED`、`LEGACY_MODULE_IDS_MISSING`、`LEGACY_DESIGN_REFS_MISSING`、`LEGACY_INPUTS_MISSING`、`LEGACY_OUTPUT_INFERRED`、`LEGACY_DEPENDENCY_REASON_PLACEHOLDER`、`LEGACY_PRIORITY_DEFAULT`、`LEGACY_ESTIMATE_PLACEHOLDER`、`LEGACY_CONFIG_INFERRED`、`LEGACY_CAPACITY_MAPPED`、`LEGACY_ACCEPTANCE_MISSING`（均为警告，需人工复核后清零）。

迁移后的聊天计划可被 `validate_task_plan` 接受（0 错误），但因缺设计条目引用会产生 `TASK_DESIGN_REF_EMPTY` 警告；迁移后的规格因 `modules`/`design_items` 为空会被阻断——这正是 V02“只给一句意图时给出缺口、不宣称覆盖完整产品”的预期表现，补全后才允许确认。

## 12. 团队使用方式

| 成员 | 使用方式 |
| --- | --- |
| 成员 1（规格/任务界面） | 用 `contract_schemas()["design_spec"]`、`["task_plan"]` 生成表单校验与错误提示；错误展示直接用 `issue.field_path/object_id/message/suggested_action` |
| 成员 2（PM 规划） | 输出 `TaskPlan` 前用 `from_dict(TaskPlan, ...)` 自检；生成结果必须走 `validate_task_plan`，`blocked` 时最多一次修订（V03） |
| 成员 4（编排） | 只消费校验通过的 TaskPlan；输出 `ExecutionPlan` 后用 `validate_execution_plan` 复核；不得重造任务 ID，边方向前置→当前 |
| 成员 5（API/持久化） | 以 `to_jsonable(report)` 作为响应/落库格式；`expected_revision` 不符返回 409；报告 `content_digest` 与 `validation_ref.report_digest` 用于 V14 导出核对 |
| 成员 6（演示/导出） | 图表/列表/导出统一读 `ExecutionPlan`；导出包保留 `plan_ref`、摘要与报告引用，界面明示 `generation_mode` |

约定：契约字段变更必须先改 `models.py`，再 `export_schema --write`、`build_fixtures --write`，随 PR 附带 Schema/fixture 变更说明；不得手改 `.schema.json`。

## 13. 运行、CI 与限制

本地命令（Python 3.11+，零第三方依赖）：

```bash
python -m unittest discover -s backend/tests -t . -v
python -m backend.app.contracts.export_schema --write   # 模型变更后导出 Schema
python -m backend.tools.build_fixtures --write          # 模型/fixture 变更后重算派生文件
```

CI（`.github/workflows/contracts.yml`）：Schema 与模型一致 → 派生 fixture 最新 → 契约/校验 unittest。对应协作规范 8.1“契约/模板”检查矩阵。

已知限制（成员 3 不负责的部分）：

- 不实现 API、持久化、前端、规划模型与编排算法；执行计划样例中的批次是固定样例，容量自适应排批由成员 4 完成。
- `P1` 仿真运行（SimulationRun）未纳入本版契约，留待后续阶段。
- 设计条目 `kind` 目前为自由字符串（仅要求非空），如需固定枚举由规格负责人与成员 3 共同升级 `schema_version`。
- 校验器不自动修复数据（不删边、不改任务），只报告问题与建议。
