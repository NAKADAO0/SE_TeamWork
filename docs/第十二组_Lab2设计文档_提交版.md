# 设计规格驱动的软件工程任务规划与可视化编排系统

软件工程课堂作业二 · 第十二组 · 设计文档 · V1.1 · 2026-11-15

## 摘要

本项目面向软件开发过程中的规划环节，设计一个能够重复用于不同产品的工作流原型。系统接收已经形成的产品设计规格，通过 PM Agent 提取交付目标、拆分实现与验证任务，再由确定性编排器检查任务图并计算资源约束下的执行批次，最终提供可编辑的任务列表、依赖关系图和版本化计划包。设计将产品事实、工作流策略和编排规则分别建模，使产品变化通过输入规格体现，流程变化通过模板与配置体现。聊天产品、内容社区和第三类现场规格用于验证同一流程的适用性。本报告说明系统结构、数据契约、核心算法、交互方案、验收场景及六人团队的开发协作安排。

关键词：软件工程工作流；PM Agent；任务分解；DAG；可视化编排

## 1. 项目任务与交付边界

### 1.1 在软件开发全流程中的位置

完整软件开发过程涉及需求、设计、规划、实现、验证和交付。本次作业实现其中从设计产物到开发计划的衔接：上游交付明确的设计规格，本系统将其转为具备输入、产物、验收条件和依赖的任务，供后续执行环节消费。

系统的使用对象是需要制定或调整开发计划的项目成员。一次使用的核心问题是：当前设计需要哪些交付任务，哪些可以同时开展，哪些必须等待其他任务，以及这些安排依据什么规则形成。

### 1.2 输入、处理与输出

| 环节 | 交付内容 | 边界说明 |
| --- | --- | --- |
| 输入 | DesignSpec、工作流模板、角色能力及容量配置 | 输入包含产品设计事实；模板不保存特定产品的固定任务答案 |
| 任务规划 | PM Agent 生成 TaskPlan | 给出目标、产物、验收、角色、来源与依赖建议，结果先作为草稿 |
| 执行编排 | 编排器生成 ExecutionPlan | 验证任务与依赖，计算拓扑层、执行批次及角色槽位绑定 |
| 用户交互 | 列表、DAG、问题定位、修订与版本确认 | 列表和图使用同一个计划修订，不单独维护业务副本 |
| 输出 | 任务分解、可视化编排、JSON 与 Markdown 计划包 | 执行计划可以交给后续执行器；本次不要求完成输入产品的编码 |

“我要做微信”表达产品意图，但没有限定功能范围和验收口径。此类输入进入缺口检查，用户补充设计后再规划。课堂案例使用范围明确的“聊天 MVP”或“内容社区 MVP”，避免将产品名称等同于完整设计。

### 1.3 功能优先级

P0 交付规格输入与确认、真实 PM 调用、任务编辑、规则校验、编排计算、图表联动、版本保存和计划导出。P1 在主流程稳定后加入模拟执行、画布连线编辑和更多导入格式。实际编码 Agent、代码沙箱、发布审批及完整质量治理在最终项目中继续扩展。

本设计不使用预先写死的产品任务表作为通用能力的实现。演示回放可用于界面联调与服务异常时的展示，但需要明确标注；规划质量的验收仍需保留真实模型调用及人工检查记录。本文的案例与验收表属于设计内容，不表示原型已经运行通过。

### 1.4 可运行 Demo 与本轮开发起点

基线为 feat/lab2-demo 分支提交 97b75e6。浏览器工作台读取自定义产品 JSON，按每项需求生成一个实现任务和一个验证任务。编排器按前置依赖、任务编号及全局并发上限计算批次。当前计划在同一标签页内保存，可查看依赖箭头、点击节点检查验收条件或导出 JSON。

| 场景 | 当前可观察结果 | 下一阶段的设计目标 |
| --- | --- | --- |
| 自定义产品 | workspace.html 支持 product、requirements；每条需求含 id、goal、acceptance | 兼容旧 JSON，补齐模块、接口、范围与来源后确认 DesignSpec |
| 两份完整案例 | 聊天案例 8 节点、11 条边、6 批；内容社区 8 节点、10 条边、5 批。并发上限均为 2 | 保留案例作为回归数据，另用第三类现场规格检验真实 PM 的规划质量 |
| 图谱与版本 | graph.html 可浏览预编排案例和本标签页生成的计划，sessionStorage 保存最近计划 | 从服务端按 plan_id 和 revision 查询，关联任务编辑、校验定位及版本导出 |
| 编排与验证 | compiler.js 检查重复编号、缺失前置和环，按全局容量排批 | 加入角色槽、优先级、产物引用、覆盖检查和可解释的等待原因 |

完整案例文件中的 mode 为 curated_example，应在历史导入与界面中保留“预编排案例”标识。fixture_replay 专指回放已保存的生成响应。用户选择“用此规格重新规划”时，工作台创建独立计划，并保存实际生成模式。

基线验证包括三项 Node 测试，以及在本地 HTTP 服务上用 Chrome 检查两个案例的实际节点与连线。第 8 章 V01–V14 是正式原型的验收目标；完成记录需要绑定实现提交、输入规格和实际结果。图 3 为目标界面示意。

## 2. 系统结构与协作链路

### 2.1 组件划分

系统采用前后端分离的单体原型。后端使用 Python 组织领域服务与 API，前端提供规格编辑和图形工作台，SQLite 保存输入、草稿、报告和确认版本。单进程部署即可支撑课程演示，暂不引入消息队列或分布式调度。

```diagram architecture
系统组件与共享数据
```

| 组件 | 主要工作 | 对外交付 |
| --- | --- | --- |
| 规格接入服务 | 解析输入、保留原文、检查完整性并组织确认 | 规范化 DesignSpec 与缺口清单 |
| PM 规划服务 | 根据规格和模板提出任务及依赖，处理有限修订 | TaskPlan、假设和澄清问题 |
| 计划校验服务 | 检查结构、引用、覆盖、产物绑定和无环性 | 与修订绑定的 ValidationReport |
| 编排计算服务 | 按依赖和容量生成可解释的顺序与并行批次 | ExecutionPlan 与等待原因 |
| 计划管理服务 | 组织异步作业、保存修订、确认版本和导出 | API、历史候选和固定计划包 |
| 可视化工作台 | 展示与编辑任务，联动依赖图、批次和详情 | 用户修订、确认请求与图形视图 |

PM 负责提出业务计划；规则服务负责判断合法性；编排服务负责计算安排。模型生成内容不能直接改写确认状态，也不能跳过规则服务派发任务。

### 2.2 人与系统的责任划分

用户提供产品设计、选择模板、处理问题并确认计划。PM Agent 形成规划建议；编排器执行既定计算规则。后续接入的执行器只能按固定计划接收任务并返回结果，不反向更改产品范围。

开发团队的六名成员负责实现这些能力，并非平台中的六个 Agent。原型只需要一个承担项目规划职责的 PM Agent；不为对应人数而增加无必要的模型角色。

### 2.3 一次规划的处理链

```diagram lifecycle
输入确认与计划生成闭环
```

用户首先提交规格。JSON 直接进入结构检查；文本先标准化，用户核对提取结果后确认。服务端冻结规格、模板和配置快照，启动规划作业。PM 产出任务草稿后，系统执行校验；存在问题时显示到具体任务或字段，交由 PM 有限修订或用户编辑。

当当前修订满足编排条件时，编排器计算依赖层、资源批次和角色绑定。用户在工作台检查并确认，系统将该修订保存为只读版本。后续修改派生新草稿，旧计划及其依据仍可查询。

生成完成、校验通过、编排完成和用户确认分别记录，不能用其中任意一步代替整个闭环。布局坐标的调整只影响显示；修改任务或依赖则使当前编排结果需要重新计算。

## 3. 设计规格与流程定制

### 3.1 规格的最低信息要求

| 信息类别 | 必须表达的事实 | 处理规则 |
| --- | --- | --- |
| 产品范围 | 目标、首期功能、明确排除项 | 无法确定边界时暂停确认，避免将任意想法扩成完整产品 |
| 需求条目 | 稳定 ID、行为描述及验收条件 | 任务通过 ID 关联；不能只有大段无来源的描述 |
| 模块职责 | 模块 ID、职责、关联需求和已知依赖 | 支撑任务分解，不要求一个模块只生成一个任务 |
| 设计内容 | 相关页面、接口、数据实体、异常及一致性规则 | 按项目适用性提供；不适用项须说明原因 |
| 约束条件 | 技术栈、运行平台、安全限制、已有基础设施 | 未指定与不适用分别记录，不由模型暗中决定 |

推荐输入 JSON 或 UTF-8 Markdown/TXT。文本提取时保留来源段落与原文，避免规范化后无法追溯。PDF 自动解析属于增强项，不作为主流程前提。

设计已明确的接口直接成为任务输入，不再机械生成同名设计工作。关键规则缺失时要求补充；若只是允许开发者选择的实现细节，则记录允许范围，并在相应任务中交付和验证。

### 3.2 统一对象与版本含义

| 对象 | 标识方式 | 关键内容 |
| --- | --- | --- |
| DesignSpec | spec_id + version | 产品范围、需求、模块、设计条目和约束 |
| WorkflowTemplate | template_id + version | 阶段、角色、分解原则与校验要求 |
| TaskPlan | plan_id + revision | 某一输入快照产生的任务、建议依赖与问题 |
| ExecutionPlan | execution_plan_id + plan_ref | 归一化图、批次、绑定、配置及校验引用 |
| SimulationRun（P1） | run_id + 固定 plan_ref | 一次模拟运行及其任务尝试记录 |

schema_version 独立表示数据格式版本。输入版本、计划修订和格式版本不能混用。服务端计算规范化 JSON 的内容摘要；对象键按固定顺序编码，数组保留契约要求的顺序，原始文本另行保存。

### 3.3 模板如何支持不同工作流

模板定义可变化的规划策略，例如阶段组织、允许角色、任务粒度建议和验证要求；运行配置定义本次使用的并发数和角色容量。模板可在多个产品之间复用，同一规格也可以选择不同模板形成不同规划。

P0 将模板作为版本化配置文件管理，界面允许选择模板并修改受支持的参数。模板自身由规则检查限制，不能把用户输入转换成工具授权。产品名称只用于描述与展示，不作为选择固定任务图的判断条件。

| 配置项 | 例值 | 影响 |
| --- | --- | --- |
| stages | implement、verify、integrate | 任务分组与显示，不自动生成跨阶段全连接依赖 |
| allowed_roles | backend、frontend、qa | PM 可选角色与能力合法性检查 |
| require_verification | true | 每项范围内需求应有关联实现任务与验证任务 |
| max_concurrency | 2 | 静态批次的全局任务数量上限 |
| role_capacity | backend=1、frontend=1、qa=1 | 各类角色同时可承担的任务数 |
| ordering | priority、task_id | 就绪候选的确定性排序 |

通用性通过更换合格规格而不改业务代码验证；可定制性通过修改模板或容量观察任务组织与编排变化验证。两者分别检查，避免把“可换产品名”当作流程通用。

## 4. PM Agent 与任务建模

### 4.1 规划输入与生成步骤

PM 接收经用户确认的 DesignSpec、模板、当前配置和可用角色列表。提示模板使用跨产品的软件工程规则，要求模型围绕交付成果拆分任务，保留稳定需求与设计引用。

1. 建立范围内需求、模块、接口和约束的索引，识别需要交付的能力。
2. 拆分实现任务；每项聚焦一个主要交付目标，并明确输入、产物和验收。
3. 为需求配置验证任务，为跨模块路径配置必要的集成验证。
4. 按产物生产与消费关系建议前置任务，并写出依赖原因。
5. 为任务配置阶段、角色、优先级和有依据的估算。
6. 输出结构化 TaskPlan，同时列出假设和待澄清问题。

共享环境和基础设施任务应当有设计依据，不无条件加入全部项目。“完成前端”“完成后端”过于宽泛；按每个函数拆项又会增加管理噪声，二者均通过任务粒度检查与人工复核调整。

### 4.2 任务卡契约

| 字段组 | 字段 | 约束与用途 |
| --- | --- | --- |
| 身份与目标 | id、title、description | ID 在计划内唯一；目标对应可检查的主要交付物 |
| 规格追溯 | requirement_ids、module_ids、design_refs | 引用固定规格中存在的条目 |
| 分类与分配 | kind、stage、role | kind 为 implementation、verification、integration 或 support；阶段和角色来自模板 |
| 数据契约 | inputs、outputs | 说明资料来源、产物类型与消费关系 |
| 完成判断 | acceptance | 可检查的预期结果，不能只有“全部完成”等泛化说明 |
| 依赖关系 | depends_on | 前置 task_id 与 reason；边从前置指向当前任务 |
| 规划参数 | priority、estimated_effort | 优先级为非负整数，数值越小越优先；估算包含值、单位与依据 |

工作量用于规划参考，不等于模型运行时长或实际交付日期。模板可建议任务粒度，系统不以固定人日区间强行判定所有任务合法性。

### 4.3 产物引用与任务片段

产物类型采用 design_contract、implementation、verification_report、integration_report 和 support_artifact。每个输出在所属计划内有唯一引用。输入分为外部设计引用和任务产物引用，二者都必须能找到实际来源。

下面给出聊天规格中一个验证任务的精简片段，其中 T-MSG-API 已在同一计划内定义，并声明 O-API 实现产物：

```json
{
  "id": "T-MSG-VERIFY",
  "title": "验证文本消息发送与查询",
  "kind": "verification",
  "stage": "verify",
  "role": "qa",
  "requirement_ids": ["R-MSG-01"],
  "module_ids": ["M-MSG"],
  "design_refs": ["I-SEND", "I-LIST"],
  "inputs": [
    {"source": "design", "ref": "I-SEND", "type": "design_contract"},
    {"source": "task_output", "ref": "T-MSG-API/O-API", "type": "implementation"}
  ],
  "outputs": [
    {"id": "O-VERIFY", "type": "verification_report", "description": "消息验证报告"}
  ],
  "acceptance": ["发送成功后查询会话，结果包含相同消息 ID"],
  "depends_on": [
    {"task_id": "T-MSG-API", "reason": "需要可调用的消息接口实现"}
  ],
  "priority": 1
}
```

完整 TaskPlan 还包含任务 description、估算、输入引用、生成模式、假设和澄清项等字段。片段用于说明数据衔接，不作为可直接确认的完整规划结果。

P0 要求直接消费任务产物时显式声明对生产任务的直接依赖，即使已有间接路径。仅用于顺序约束的边可以不绑定产物，但必须说明业务或技术理由。

### 4.4 生成失败与语义质量

模型适配层暴露规格标准化和计划生成两个能力，调用分别设置超时与输出上限。JSON 或结构检查失败后，最多进行一次携带错误明细的修订调用；仍不合法则保存候选与问题，由用户继续处理。

关键设计缺口进入 needs_clarification，不通过模型自动编造来消除。认证失败、限流和超时分别记录原因。离线规则模式与样例回放需要用户显式选择，并在界面、报告和导出中保留 generation_mode。

规则覆盖率只证明引用完整。规划语义还需人工检查：任务是否贴合业务、异常路径是否遗漏、依赖理由是否成立、验收是否可操作。检查记录与计划修订一同保存，不能用模型自评替代。

## 5. 计划校验与确定性编排

### 5.1 编排准入条件

校验器产出统一问题对象，至少包含 code、severity、object_id、field_path、message、related_ids 和 suggested_action。error 阻止编排与确认；warning 需要在确认时记录处理意见。报告固定引用一个计划修订和内容摘要。

| 检查面 | 判定规则 | 典型反馈 |
| --- | --- | --- |
| 数据结构 | 必填项完整、ID 唯一、字段类型合法 | 指出缺少的验收字段或重复任务 ID |
| 来源引用 | 需求、模块、设计条目均存在且版本一致 | 标明不存在的 requirement_id |
| 需求覆盖 | 范围内需求均有关联实现与验证任务 | 列出只有实现而没有验证的需求 |
| 图结构 | 前置存在，无自依赖和有向环 | 展示一条真实闭合环路径 |
| 产物连接 | 输出存在、类型相符，消费者有生产者依赖 | 定位无法解析的 inputs 引用 |
| 角色与容量 | 角色可用，容量和全局并发均为正整数 | 提示缺失角色或容量配置错误 |
| 修订与约束 | 校验引用当前修订，已知直接冲突已处理 | 拒绝沿用旧报告或违反明确范围的任务 |

无法可靠程序判定的语义冲突作为人工检查事项展示，不声称自动规则能够理解全部设计含义。发现环时不擅自删边；拓扑排序中剩余的下游节点应称为“受环影响”，不能全部称为环内节点。

### 5.2 从任务到执行图

系统使用 DAG（有向无环图）表达任务依赖。TaskPlan 中的任务直接成为执行图节点，depends_on 归一化为有向边，不重新生成另一套无法追溯的任务 ID。拓扑层仅表示依赖关系，资源批次进一步考虑全局并发与角色容量。

一个阶段中的任务可以分布在不同拓扑层。只要依赖与资源允许，某模块的验证可以在其他模块仍实现时进行。与已确认接口进行 mock 对接的前后端任务不必人为串行；实际联通检查则等待双方实现产物。

P0 输出静态、保守的执行批次：同批任务可同时开展，下一批等待上一批结束。该安排便于解释和复现，未承诺最短工期。事件驱动的动态调度在模拟执行阶段扩展。

### 5.3 批次计算规则

```text
输入：已校验的 tasks、固定 config、角色能力快照
按依赖求出 topological_levels
完成推演集合 = 空；待安排集合 = 所有任务
当待安排集合非空时：
  取前置全部位于完成推演集合的候选任务
  按 priority 升序、task_id 升序排序
  按全局并发和角色容量依次装入当前批次
  如当前批次为空，报告阻塞原因并停止
  保存批次、角色槽位及其他候选等待原因
  从待安排集合移除本批任务，加入完成推演集合
返回执行图、拓扑层、批次和绑定
```

每个任务占用一个全局槽与一个角色槽；同角色优先使用编号最小的空闲槽。暂时无法放入的候选不阻断后续其他角色任务的检查。

“完成推演集合”只用于静态计算，不改变任何运行状态。相同 TaskPlan、模板和配置应产生相同节点、边、批次与绑定，时间戳等元数据除外。PM 多次调用的输出不要求完全相同，模型生成与编排计算的可复现性分别说明。

### 5.4 编排结果与可解释性

ExecutionPlan 保存 plan_ref、规格/模板/配置摘要、nodes、edges、topological_levels、batches、bindings 和 validation_ref。每项任务必须被安排一次，每条边的生产者必须位于消费者之前，所有批次不得超出容量。

依赖等待和资源等待分开显示。例如“等待消息 API 实现产物”与“qa 容量已满”应有不同原因。全部节点安排完毕才标记 compiled，用户确认后转为 confirmed。仍有未安排任务而没有候选时，应返回阻塞而非成功。

P0 不把人日估算直接换算为日历计划。若后续增加关键路径或时间线，需要先明确任务持续时间、人员工时与容量假设，再显示预测值。

### 6.1 页面与操作路径

工作台围绕一个当前计划组织三个视图：规格与配置视图负责输入，规划工作台负责任务与图，版本视图负责确认、历史和导出。公共导航保留当前 spec_ref、plan_ref、生成模式和处理状态。

```diagram workspace
规划工作台布局示意
```

| 区域 | 显示内容 | 支持操作 |
| --- | --- | --- |
| 规格与配置 | 产品范围、来源、缺口、模板及容量 | 导入、核对标准化结果、确认规格、发起生成 |
| 任务列表 | ID、目标、角色、依赖、校验标记 | 增删任务、编辑字段和依赖、查看详情 |
| 依赖图 | 节点、前置边、阶段/角色、拓扑层 | 选中节点、缩放、定位问题和查看批次 |
| 任务详情 | 输入输出、验收、设计引用与依赖原因 | 修改草稿，回到来源条目 |
| 校验与批次 | error/warning、容量、等待原因 | 定位错误、重新校验与编排 |
| 版本与导出 | 固定输入、修订、确认人及导出格式 | 确认、查看历史、派生新草稿、导出 |

### 6.2 图、列表和修订的一致性

列表与依赖图共享后端返回的任务和边。选中任务时，列表、图和详情同步定位；点击校验问题时跳到对应节点或字段。节点拖动仅保存布局信息，不改变 TaskPlan。

P0 通过表单选择前置任务即可完成依赖编辑，自由连线属于增强功能。删除被其他任务引用的节点前显示影响，由用户提交一致修订，或保留错误草稿继续处理，禁止无提示自动重连。

修改任务、边或容量后显示“待重新编排”。正在查看的旧报告保留原修订标签，不能继续作为新版本的确认依据。确认版只读，修改入口创建新草稿。

### 6.3 展示语义与可访问性

节点显示短标题、任务 ID 和角色，完整内容在详情面板中查看。角色用配色区分，错误和警告另配文本、图标及高亮边，不仅靠颜色传达状态。默认布局由左向右，较大图支持缩放和按批次聚焦。

规划界面展示“草稿、已校验、已编排、已确认”，不显示虚构运行进度。生成模式标为 live_llm、offline_rule 或 fixture_replay 的可读名称，模拟运行结果也必须单独标注。

## 7. 服务接口、持久化与一致性

### 7.1 关键 API

| 接口 | 作用 | 关键输入或结果 |
| --- | --- | --- |
| POST /specs | 提交 JSON 或文本规格 | 返回标准化草稿或字段问题 |
| POST /specs/{id}/confirm | 确认规格 | expected_version，锁定本次输入 |
| GET /templates | 查询模板 | 模板版本与允许配置 |
| POST /planning-jobs | 异步规划 | spec_ref、template_ref、config、mode；返回 202 和 job_id |
| GET /planning-jobs/{id} | 查询生成进度 | 状态、错误及成功后的 plan_ref |
| GET /plans/{id} | 读取指定修订 | revision 与 TaskPlan |
| PUT /plans/{id} | 保存草稿修订 | expected_revision 和完整任务草稿 |
| POST /plans/{id}/validate | 校验固定修订 | ValidationReport |
| POST /plans/{id}/compile | 生成执行计划 | ExecutionPlan 或阻塞问题 |
| POST /plans/{id}/confirm | 确认当前编排 | revision 与 execution_plan_id |
| GET /plans/{id}/export | 输出计划包 | revision、json/markdown 格式 |

领域错误采用统一对象，包含 code、message、details 和 request_id。请求解析失败返回 400，不存在返回 404，修订或状态冲突返回 409，字段或领域规则失败返回 422；模型暂不可用可返回 503。异步作业执行中的失败通过作业查询返回结构化 error。

### 7.2 作业状态与数据存储

规划作业状态包括 pending、running、needs_clarification、succeeded、invalid_output 和 failed。需要补设计时返回 needs_clarification；有限修订仍不合法时进入 invalid_output；调用服务异常进入 failed。用户补充输入后创建新作业，不把旧失败记录覆盖为成功。

| 存储对象 | 持久化内容 | 一致性要求 |
| --- | --- | --- |
| 规格与模板 | 原文、结构化内容、版本及确认信息 | 已确认输入保持不可变 |
| 计划修订 | TaskPlan、输入快照、模式与生成元数据 | 每次编辑追加修订 |
| 作业 | 请求快照、进度、结果和错误摘要 | 结果绑定提交时输入 |
| 校验与编排 | 报告、ExecutionPlan、摘要与引用 | 只作用于指定修订 |
| 展示布局 | plan_ref 和节点坐标 | 不参与业务合法性和排序 |

原型可用 JSON 列保存任务图，避免过早拆分大量关系表；查询、修订和确认由统一 repository 层负责。不同领域服务不直接改写其他模块拥有的状态。

### 7.3 防止陈旧结果覆盖

草稿更新携带 expected_revision。服务端在事务中核对当前修订，陈旧请求返回 409。新修订不继承有效的校验和编排结果，旧报告仍留历史。

模型任务绑定输入快照。若用户在生成期间改变输入，返回结果只作为原快照的历史候选，不覆盖当前草稿。确认操作再次核对修订、摘要、错误数、警告处理记录和执行计划引用，不能相信前端自行提交的“已通过”状态。

导出固定一个修订，包含设计、模板和配置快照、任务、执行图及校验记录。运行时凭据不进入导出。设计 JSON 可重新导入；完整计划包在 P0 用于复查，不要求直接恢复成可编辑工程。

### 7.4 运行配置与安全边界

模型密钥保存在服务端环境变量中，日志隐藏凭据，记录模型标识、提示版本、耗时和可获取的用量信息。上传规格与任务描述均作为数据，不接受其中要求改变系统权限的指令。

P0 面向本地单用户演示，默认不开放真实代码写入或发布工具。若后续部署为多人在线服务，再增加身份认证、项目范围权限与访问审计；当前设计不宣称已经具备生产级多租户能力。

输入设计限定为：复用现有登录会话，提供单聊文本发送、会话查询、历史分页和无权限访问拒绝；不包含群聊、支付或音视频。接口、页面状态和异常返回由规格事先定义。

| T-E2E | 发送后查询会话的端到端验证 | T-API-V、T-UI-V | qa |

聊天案例的任务依赖与外部设计输入

当所有优先级相同时，全局并发为 2，backend、frontend、qa 容量均为 1，得到 [T-API, T-UI] → [T-API-V] → [T-UI-V] → [T-E2E]。若全局并发改为 3 且 qa 容量为 2，则验证任务可同批执行，变为 [T-API, T-UI] → [T-API-V, T-UI-V] → [T-E2E]。

### 8.2 内容社区与现场输入

第二类规格为内容社区 MVP，范围包含图文笔记发布、内容流、点赞与评论，排除直播和推荐算法训练。预期任务涉及媒体校验、笔记存储、内容流交互、点赞幂等与评论验证等设计事实，不能仅替换聊天任务标题。

第三类使用未预置的现场设计，例如校园失物招领 MVP。更换规格时不修改规划、校验和编排代码，保留真实调用、输出及人工检查结果。同时增加两类扰动检查：只改产品名称不应引入新功能；新增需求或设计约束应反映到任务、覆盖或问题清单中。

### 8.3 规则与交互验收矩阵

| 编号 | 操作或输入 | 预期表现 |
| --- | --- | --- |
| V01 | 提交合格规格并走完主流程 | 可得到任务、编排、图与固定版本导出 |
| V02 | 输入只有一句产品意图 | 给出缺口，不宣称覆盖完整产品 |
| V03 | 模型输出非法 JSON 或缺字段 | 最多一次修订，仍失败则保留问题 |
| V04 | 删除某需求的验证任务 | 覆盖错误定位到需求与相关任务 |
| V05 | 设置缺失前置、自依赖或环 | 拒绝编排，环给出真实闭合路径 |
| V06 | 输入引用不存在的任务产物 | 定位 inputs 与生产者，阻止确认 |
| V07 | 相同输入重复编排 | 节点、边、批次和绑定保持一致 |
| V08 | 改变存在并行空间的图的容量 | 批次相应变化且无超额分配 |
| V09 | 编辑已编排或已确认内容 | 新草稿需重算，历史版本不受覆盖 |
| V10 | 提交陈旧修订更新或确认 | 返回 409，不污染当前计划 |
| V11 | 图中定位任务、修改依赖并导出 | 列表、图与导出任务/边一致 |
| V12 | 用两类产品和第三类现场规格运行 | 同一流程产出对应领域任务 |
| V13 | 模型故障或用户选择样例回放 | 明示错误或实际模式，不伪装实时生成 |
| V14 | 读取固定修订的导出包 | 来源、配置、任务与报告引用可核对 |

自动化验证覆盖结构、依赖、容量、版本和接口规则；固定 fixture 用于持续集成。真实模型结果另由人工检查任务贴合度、验收可操作性、依赖合理性与约束遵循情况。不能以一次演示成功代替规则测试，也不能以结构覆盖率代替语义质量。

### 8.4 完成指标与展示安排

确认计划需达到：范围内需求的实现和验证关联覆盖率均为 100%，没有阻断错误，任务图无环，批次及绑定合法，图与导出一致。语义检查中发现的问题必须记录处理结论。生成耗时、修订次数和人工调整量按实际情况记录，不预设效率改善。

展示规模以 10 至 50 个任务为主，用 50 节点固定图检查缩放、选中和定位是否可用。课堂按“说明边界—输入规格—生成任务—编排展示—修改容量—制造错误—更换产品—导出”的顺序演示。实时服务异常时可以使用标明模式的回放，真实生成验收仍需补充实际证据。

### 9.3 Git 分支与提交约定

采用 main + 短期功能分支 + Pull Request。main 保持可启动，功能按可验收单元拆分，不设置长期个人开发分支。分支命名为 feat/编号-主题、fix/编号-主题、docs/编号-主题 或 chore/编号-主题；编号关联实际 Issue。

提交格式为 type(scope): 说明，例如 feat(planner): generate task plans from design specs。feat 表示功能，fix 表示修复，docs 表示文档，test 表示测试，refactor 表示行为不变的结构调整，chore 表示配置和工具。单次提交不混入无关格式化或重构。

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/12-pm-plan
# 实现后检查实际文件，运行相关验证，再暂存指定路径
git status --short
git add backend/app/planner backend/tests/planner
git diff --cached
git commit -m "feat(planner): generate task plans from design specs"
git push -u origin feat/12-pm-plan
```

编号和路径仅为约定示例，创建对应 Issue 与模块后使用。独占分支可 rebase 更新，共享分支使用 merge；main 和共享分支禁止强推。冲突需理解两侧改动，公共契约与迁移由相关负责人共同确认，不能直接全选一侧覆盖。

### 9.4 评审、检查与版本发布

PR 说明关联问题、改动后的行为、契约影响、验证结果、演示步骤和已知限制。至少一名非作者批准；公共契约、迁移和编排规则需相关负责人或其指定替补复核。受影响调用方确认兼容、适用检查通过后使用 squash merge，随后删除功能分支。

CI 运行后端相关测试、前端类型检查与构建、共享 fixture 和必要的端到端主链。持续集成不调用付费实时模型，模型质量以脱敏人工记录补充。main 的保护和必需检查需在远程仓库管理设置中落实。

环境配置使用 .env.example 说明变量，不提交 .env、密钥、本地数据库、运行日志、缓存、虚拟环境、node_modules 或构建目录；依赖锁文件、模板、规范化示例及选定验收结果应提交。文本统一 UTF-8，代码与配置统一换行策略。

每项工作完成需具备可运行交付物、适用验证、接口与文档更新、非作者评审和已合并结果。课堂交付标签采用 v1.0.0-lab2，指向通过检查的 main 提交。共享主干出现回归时通过修复或 revert PR 恢复，不用强推改写历史。

## 10. 扩展路径与交付清单

### 10.1 模拟执行与最终项目接入

P1 模拟器读取已确认 ExecutionPlan，用虚拟产物演示 pending、ready、running、succeeded 及 failed/cancelled。只有前置模拟成功且资源可用才派发。暂停阻止新派发，取消终止剩余工作；重试创建新 attempt_id，旧尝试结束后才可重新安排。

回调按 run_id、task_id、attempt_id 和 plan_ref 核对，重复事件只生效一次。进程重启后可将未结束模拟运行标为 interrupted，保留历史并由用户选择重新运行，不宣称无缝恢复。模拟成功只证明演示规则完成，不证明案例产品已经开发成功。

最终项目通过上游 DesignSpec 和下游 ExecutionPlan 接口接入本模块，再扩展真实开发、测试、成果评审与交付能力。角色注册、产物引用与版本约束保持稳定，真实成果完成条件则增加证据与审核记录。

### 10.2 风险及应对

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 输入缺乏关键设计 | PM 容易补造业务规则 | 规格确认、关键缺口阻断与假设显式记录 |
| 结构合法但任务不合理 | 规划难以实际执行 | 规则验证结合统一人工质量检查 |

### 10.3 交付材料

最终提交包括设计报告、可启动源码、输入/任务/编排契约、版本化模板、三类设计规格、实际计划导出、规则测试与人工检查记录、启动说明及课堂演示材料。报告中的验收方案在实现后填写实际结果，未执行项目不记录为通过。
