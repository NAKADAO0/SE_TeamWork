职责边界：**编排消费已校验的计划**。引用是否有效、需求覆盖是否完整、产物能否解析、是否存在环，都是成员 3 校验器的判定；编排只核对“报告绑定的是不是当前修订、是否有 error”，再按规则计算。编排不删边、不改任务、不新增无法追溯的任务 ID。

## 2. 输入与输出

### 2.1 输入

| 输入 | 必需字段 | 用途 |
| --- | --- | --- |
| TaskPlan | `plan_id`、`revision`、`config`、`tasks` | 计算主体；任务只读取 `id / role / stage / priority / depends_on` |
| `config` | `max_concurrency`、`role_capacity`、`ordering` | 资源约束与候选排序 |
| `depends_on` | `task_id`、`reason` | 归一化为边；`reason` 进入等待原因的业务解释 |
| DesignSpec / WorkflowTemplate | `spec_id+version` / `template_id+version` | 计算 `spec_digest`、`template_digest`，并核对计划引用版本 |
| ValidationReport | `target`、`blocked`、`issues` | 编排准入；`report_digest` 写入 `validation_ref` |

任务的其他字段（标题、输入输出、验收、估算）不参与计算，也不在此层复制：列表、详情与导出继续读任务计划原文。

### 2.2 输出

`OrchestrationResult` 有两份文档，一份进契约、一份做解释：

| 文档 | 内容 | 消费方 |
| --- | --- | --- |
| `result.document()` | ExecutionPlan：`nodes`、`edges`、`topological_levels`、`batches`、`bindings`、三个摘要、`plan_ref`、`validation_ref` | 成员 5 存 `artifacts(kind="execution")`；成员 6 画图与批次视图；导出 |
| `result.explanation_document()` | 逐批容量占用与等待原因（不属于 ExecutionPlan 契约），见第 4 节 | 成员 6 的“校验与批次”面板、成员 1 的作业状态、导出附加页 |

输出顺序固定：`nodes` 按任务计划声明顺序；`edges` 按“消费者任务声明顺序 + `depends_on` 声明顺序”去重；`topological_levels` 层内按 `priority`、`task_id` 升序；`batches` 按排批顺序；`bindings` 与批次同序。

## 3. 算法

### 3.1 处理步骤

```text
1 准入：报告 target == (task_plan, plan_id, revision) 且 blocked=false；否则拒绝
2 规格/模板核对：计划 spec_ref / template_ref 与传入对象版本一致，计算摘要
3 图归一化：任务 → 节点；depends_on → 边（前置 → 当前）；自依赖/未知前置/环 → 拒绝
4 拓扑层：level(t) = 1 + max(level(前置))，无前置为第 0 层
5 排批：完成推演集合 = ∅；待安排 = 全部任务
   while 待安排非空：
     候选 = 前置全部在完成推演集合中的任务
     按 ordering 排序（priority → task_id，task_id 永远兜底）
     依次装入当前批次：全局并发未满、且该角色未满
     记全局槽位 1..n、角色槽位 1..capacity（最小空闲优先）
     本批为空 → 返回阻塞；否则记录批次、绑定、其他候选的等待原因
   从待安排移除本批，加入完成推演集合
6 装配 ExecutionPlan 与解释文档
```

“完成推演集合”只存在于计算过程中，不写回任何运行状态；同批任务视为可同时开展，下一批等待上一批结束。该安排保守、可解释，不承诺最短工期（事件驱动调度属于 P1 模拟执行）。

### 3.2 资源与槽位

- 每个任务占用 **1 个全局槽 + 1 个角色槽**；同一批内全局槽不重复，同一角色槽不重复。
- 全局槽取批内位置 1..`len(batch)`，角色槽取该角色在批内的第几个（1..`role_capacity[role]`）。
- `ordering` 缺少 `task_id` 时自动追加（校验器 `CONFIG_ORDERING_NONDETERMINISTIC` 的同类保护）；`ordering` 中出现 `priority`、`task_id` 以外的键直接拒绝。
- `max_concurrency`、`role_capacity` 必须为正整数；任务使用了未配置容量的角色即拒绝。

### 3.3 示例（聊天案例，`max_concurrency=2`，三角色各 1）

| 批次 | 任务 | 全局槽 | 角色槽 | 为什么只有这些 |
| --- | --- | --- | --- | --- |
| 1 | C1 | 1 | backend 1 | 只有 C1 无前置 |
| 2 | C2、C3 | 1、2 | backend 1、frontend 1 | C2/C3 只依赖 C1 |
| 3 | C4、C6 | 1、2 | backend 1、qa 1 | C5 还缺 C4；C7 还缺 C5 |
| 4 | C5 | 1 | frontend 1 | 依赖 C3、C4 均已完成 |
| 5 | C7 | 1 | qa 1 | 依赖 C4、C5 |
| 6 | C8 | 1 | qa 1 | 依赖 C6、C7 |

节点 8、边 11、批 6、层 6；与成员 3 的 `examples/contracts/chat/execution-plan.json` **逐字段一致**（测试 `ChatParityTest`）。

## 4. 等待原因

等待原因回答“这个任务为什么不在本批”，与依赖边、批次并列展示但不改变调度结果。

| code | 含义 | 必要字段 | 示例消息 |
| --- | --- | --- | --- |
| `WAIT_DEPENDENCY` | 依赖等待：前置尚未完成 | `blocking_task_ids` | `等待前置任务 C2（复用消息查询服务与鉴权）` |
| `WAIT_GLOBAL_CAPACITY` | 资源等待：全局并发已满 | `capacity`、`in_use` | `全局并发已满（2/2），本批已排入 N2、N3` |
| `WAIT_ROLE_CAPACITY` | 资源等待：角色容量已满 | `role`、`capacity`、`in_use` | `角色 qa 容量已满（1/1），本批已排入 N6` |

前置恰好在本批内时，消息改为“本批完成后可排入（前置 C2 在本批执行）”，避免被读成阻塞。设计文档 §5.4 要求“等待消息 API 实现产物”与“qa 容量已满”分开，对应上表的依赖等待与资源等待。

解释文档结构：

```json
{
  "schema_version": "1.0",
  "execution_plan_id": "EXEC-CHAT",
  "plan_ref": {"plan_id": "PLAN-CHAT", "revision": 1},
  "config": {"max_concurrency": 2, "role_capacity": {"backend": 1, "frontend": 1, "qa": 1},
             "ordering": ["priority", "task_id"]},
  "blocked": false,
  "summary": {"tasks": 8, "batches": 6, "largest_batch": 2, "wait_reasons": 18, "topological_levels": 6},
  "topological_levels": [["C1"], ["C2", "C3"], ["C4", "C6"], ["C5"], ["C7"], ["C8"]],
  "batches": [{
    "index": 0,
    "tasks": ["C1"],
    "bindings": [{"task_id": "C1", "global_slot": 1, "role_slot": 1}],
    "capacity": {"global": {"used": 1, "capacity": 2},
                 "roles": {"backend": {"used": 1, "capacity": 1}, "frontend": {"used": 0, "capacity": 1},
                           "qa": {"used": 0, "capacity": 1}}},
    "waiting": [{"task_id": "C2", "code": "WAIT_DEPENDENCY", "role": "backend",
                 "blocking_task_ids": ["C1"],
                 "message": "等待前置任务 C1（消息 ID 与会话隔离规则需要先由契约确认）"}]
  }]
}
```

`batches[i]` 与解释文档中的 `index: i` 一一对应；每个批次里“本批任务 + 全部 waiting 任务”覆盖尚未安排的全部任务，界面可据此逐项解释。

## 5. 错误码与 HTTP 映射

| code | 触发条件 | 建议状态 |
| --- | --- | --- |
| `ORCH_VALIDATION_MISSING` | 未提供校验报告 | 422 |
| `ORCH_VALIDATION_BLOCKED` | 报告 `blocked=true`（详情带 `issues`） | 422 |
| `ORCH_VALIDATION_STALE` | 报告绑定的 `plan_id/revision` 或规格/模板版本与当前不一致 | 409 |
| `ORCH_PLAN_INVALID` | 缺少 `plan_id/revision/config/tasks`，或任务缺 `id/role/stage/priority` | 422 |
| `ORCH_CONFIG_INVALID` | 容量非正整数、`ordering` 含未知键 | 422 |
| `ORCH_ROLE_CAPACITY_MISSING` | 任务使用了未配置容量的角色 | 422 |
| `ORCH_TASK_ID_DUPLICATE` / `ORCH_DEPENDENCY_SELF` / `ORCH_DEPENDENCY_UNKNOWN` | 防御式图检查（正常已被校验器拦截） | 422 |
| `ORCH_DEPENDENCY_CYCLE` | 防御式环检测，`details.cycle_text` 给出闭合路径 | 422 |
| `ORCH_BLOCKED` | 有任务但当前批次为空（配置异常导致无法推进） | 422 |
| `ORCH_SELF_CHECK_FAILED` | `verify=True` 时输出未通过成员 3 的执行计划校验 | 500 |

`OrchestrationError` 继承 `ValueError`，`as_dict(request_id=...)` 直接给出设计文档 §7.1 的统一错误对象；陈旧报告对应修订冲突语义，因此单独给 409。

## 6. 接线

### 6.1 成员 5：完整执行计划（推荐路径）

```python
from backend.app.orchestration import OrchestrationError, compile_plan

result = compile_plan(
    plan,                      # 当前修订的 TaskPlan（dict 或契约对象）
    spec=spec,                 # 该任务计划的 spec_ref 对应规格
    template=template,         # 该任务计划的 template_ref 对应模板
    validation_report=report,  # 同一修订的 ValidationReport（校验端点刚产出的）
)
execution = result.document()              # ExecutionPlan
explanation = result.explanation_document()  # 等待原因，可存 artifacts(kind="explanation")
```

`POST /plans/{id}/compile` 的 `plan_ref`、`validation_ref` 必须来自本次修订，不要复用旧修订的编排结果；新修订不继承旧报告（设计文档 §7.3）。

### 6.2 成员 5：沿用现有注入点（最小改动）

`backend/delivery.py` 现在注入的是 `compiler(plan) -> 批次`：

```python
from backend.app.orchestration import as_compiler
from backend.api import create_app

app = create_app(compiler=as_compiler())
```

此时仍返回批次数组，旧测试与前端不受影响；`explain_batches(plan)` 可在需要时给出等待原因。代价是执行计划只剩批次与节点/边，`topological_levels`、`bindings`、摘要与 `validation_ref` 需要按新路径补上——**建议在 S2 联调时切到 6.1**。

### 6.3 成员 6：图与批次视图

- 节点：`execution_plan.nodes[].{task_id, role, stage, priority}`；边：`edges[].{from_task, to_task}`，方向固定为**前置 → 当前**，不要在前端反转。
- 层：`topological_levels` 只表达依赖先后；批次：`batches` 才是资源安排。两者不等价，容量变化只改批次。
- 槽位：`bindings[].{task_id, global_slot, role_slot}`；同一批内可据此画“槽位行”。
- 等待原因：`explanation.batches[].waiting[]`，按 `code` 分色、按 `message` 展示；不要用颜色单独承载状态（设计文档 §6.3）。

## 7. 可复现性与容量变化（V07 / V08）

| 检查 | 做法 | 实际结果 |
| --- | --- | --- |
| V07 同输入重复编排 | 同一 chat 计划连续编排两次，比较完整文档 | 节点、边、层、批次、绑定、摘要与编号完全一致 |
| V07 任务声明顺序变化 | 反转 `tasks` 数组后再编排 | 批次、层、绑定、边集合不变（节点顺序随声明顺序，属于展示顺序） |
| V07 50 节点固定图 | 10 条链 × 5 任务，`max_concurrency=4` | 每任务恰排一次、窗口合法、重复编排一致 |
| V08 降 qa 容量 | 内容社区 `qa 2 → 1` | 批次 `[[N1],[N2,N3],[N4,N5],[N6,N7],[N8]]` → `[[N1],[N2,N3],[N4,N5],[N6],[N7],[N8]]`；边集合完全相同 |

内容社区案例的对照材料见 `examples/orchestration/community-qa1/`（改动后的任务计划、重新校验的报告、执行计划与等待原因）。

## 9. 边界与未做项

1. **不重复实现校验**：引用、覆盖、产物、环的判定归成员 3；本模块的图检查是排批终止的防御，不替代校验报告。
2. **P0 只做静态批次**：不换算日历、不算关键路径、不做事件驱动重排；模拟执行的动态派发属于 P1。
3. **不改状态**：编排只读修订，不改变草稿/确认状态，也不改写任务计划；确认与导出由成员 5 负责。
4. **未改 `backend/api.py`、`backend/delivery.py`**：接线属于成员 5 的主责范围，本模块只提供两种入口与示例。
5. **未在浏览器实测**：图与批次面板的展示由成员 6 在联调时核对（V11 的编排侧）。
