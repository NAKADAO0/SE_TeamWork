## 5. 接线

### 5.1 给成员 5（API、存储、版本导出）

**推荐：完整执行计划。** 在 `POST /plans/{id}/compile` 里，用刚产出的校验报告调用：

```python
from backend.app.orchestration import OrchestrationError, compile_plan

result = compile_plan(
    plan,                      # 当前修订 TaskPlan
    spec=spec,                 # plan.spec_ref 对应规格
    template=template,         # plan.template_ref 对应模板
    validation_report=report,  # 同一修订的 ValidationReport
)
execution = result.document()                 # 存 artifacts(kind="execution")
explanation = result.explanation_document()   # 可存 artifacts(kind="explanation")
```

- 错误映射：`OrchestrationError.status` 已经是建议值（陈旧报告 409，其余输入问题 422），`error.as_dict(request_id=...)` 是统一错误对象，可直接 `raise HTTPException(error.status, detail=error.as_dict(...))`。
- 不要复用旧修订的编排结果：新修订不继承旧报告与旧执行计划（设计文档 §7.3）；`validation_ref.report_digest` 与报告摘要不一致时成员 3 的 `validate_execution_plan` 会报 `EXEC_VALIDATION_STALE`。
- `nodes` 的任务集合与任务计划严格一致，导出时不必再拼装节点；`batches` 用于 Markdown 导出即可复用现有模板。

**最小改动：沿用现有注入点。** `delivery.py` 的 `compiler(plan) -> 批次` 可以直接换成：

```python
from backend.app.orchestration import as_compiler
app = create_app(compiler=as_compiler())
```

此时 `POST /plans/{id}/compile` 的批次立刻来自真实算法（旧行为与旧测试不变），但 `topological_levels`、`bindings`、摘要与 `validation_ref` 仍缺失，建议 S2 联调时切到上面的完整路径。

### 5.2 给成员 6（可视化、集成、验收）

- 边方向：`edges[].from_task → to_task` 是**前置 → 当前**；图上的箭头不要反转，否则 V11 会与列表、导出一致性冲突。
- 层与批次不等价：`topological_levels` 只表示依赖先后，`batches` 才是资源安排。容量变化时批次会变、层和边不变，视图要能分别表达。
- 槽位：`bindings[].{task_id, global_slot, role_slot}`，同一批内 `global_slot` 即批内位置，可画“槽位行”；`role_slot` 是角色内部编号。
- 等待原因：`explanation.batches[].waiting[]`，按 `code`（`WAIT_DEPENDENCY` / `WAIT_GLOBAL_CAPACITY` / `WAIT_ROLE_CAPACITY`）区分依赖与资源，用文字 + 图标 + 颜色表达，不能只靠颜色。
- 联调样例：`examples/orchestration/chat/explanation.json`（聊天 6 批与等待原因）、`examples/orchestration/community/execution-plan.json`（8 节点社区案例）、`examples/orchestration/community-qa1/`（V08 对照：降 qa 容量前后各一份执行计划）。
- 图数据只需读 ExecutionPlan，不需要坐标；布局坐标按契约属于“展示布局”，不参与调度（设计文档 §5.4、§7.2）。

### 5.3 给成员 3（契约与校验）

- 排版算法已按你的 `ExecutionPlan` 语义实现：`topological_levels` 为最长路径分层、`batches` 满足全局与角色容量、`bindings` 同批不冲突、`config_digest` 取 `TaskPlan.config` 的摘要。聊天样例已逐字段复现。
- 本模块的环检测只在排批前做终止保护，错误码 `ORCH_DEPENDENCY_CYCLE`，与你的 `DEPENDENCY_CYCLE` 不重复报告；两条路径都用“当前 → 前置”方向，闭合路径可直接对照。
- 未新增契约字段。等待原因放在独立的说明文档里，不塞进 `ExecutionPlan`（该契约 `additionalProperties: false`）；如果团队希望把它纳入契约，需要先改模型与 Schema，再同步提供方与消费者。
- 建议：当计划 config 改变（例如降 qa 容量）时，让 `validation_ref` 随新报告更新；对照样例 `examples/orchestration/community-qa1/` 已按“改配置 → 重新校验 → 重新编排”的顺序生成。

### 5.4 给成员 1（输入与编辑）

- 前端排批替身可以换成 `compile_batches(plan)`（输入输出与 `fixtureSchedule.js` 相同），等待原因从 `explain_batches(plan)` 取，字段为 `batches[].waiting[].{code, message}`。
